Enfoque de negocio: dominio, reglas, ciclo del bulto, por qué elegimos cada patrón, reportes y roles. Se explica con palabras del negocio y diagramas, casi sin código. Si el profesor pide ver el código, pasá al enfoque técnico.

1Dominio

Cómo lo contaríamosEs un comercio con varios locales que se abastecen desde un Centro de Distribución. El problema central es que tener la mercadería físicamente no significa poder venderla: entre el CD y el local hay un viaje, un precinto y dos controles. El sistema sigue cada unidad por dónde está y en qué condición (reservada, en tránsito, pendiente, disponible, rechazada) y sólo deja vender lo disponible. Además, cada venta y devolución impacta a la vez en stock y en caja, y con eso se arman los reportes económicos por período.

Cómo se encadenan los procesos

Entidades principales, en una frase cada una:

  • Ubicación: un local o el único CD. El CD no vende; los locales tienen stock mínimo por producto.
  • Producto, Categoría y Proveedor: el catálogo. Cada uno tiene un código que no se repite, y las bajas son lógicas para conservar la historia.
  • Compra: mercadería de un proveedor que entra al CD.
  • Necesidad y Orden de reposición: el local pide, y el CD junta los pedidos en una orden CD → local.
  • Bulto y Remito: la caja física, con su precinto, y el documento que la acompaña. El bulto tiene un ciclo de vida con historial.
  • Inventario: lleva cuántas unidades hay por ubicación, producto y condición. Es el único que mueve stock.
  • Venta, Cobro y Comprobante: lo que se vende, cómo se paga y el ticket.
  • Caja: registra cada ingreso y egreso de dinero.
  • Devolución y Reintegro: el cliente devuelve parte de una venta y se le reintegra el dinero.

3Ciclo de vida del bulto

Respuesta cortaEl bulto es la caja precintada que viaja del CD al local. Pasa por Preparado → Precintado → En tránsito → Recibido → Verificado, o termina Rechazado (precinto roto o distinto) o Anulado (se desarma antes de precintar). Cada paso queda anotado en un historial que no se puede modificar, y la mercadería recién se puede vender cuando se verifican el bulto y el remito.

Qué pasa con el stock en cada paso

PasoEstado del bultoStock (condición en el Inventario)
PrepararPREPARADOCD: DISPONIBLE → RESERVADO
AnularANULADOCD: RESERVADO → DISPONIBLE
PrecintarPRECINTADOSin cambio; se fija precinto y se emite el remito
DespacharEN_TRANSITOCD RESERVADO → local EN_TRANSITO
Recibir OKRECIBIDOEN_TRANSITO → PENDIENTE (todavía no vendible)
Recibir con precinto rotoRECHAZADOEN_TRANSITO → RECHAZADO (en custodia, no vendible); remito RECHAZADO
Verificar bultoVERIFICADOSin cambio: falta el remito
Verificar remito(bulto ya VERIFICADO)PENDIENTE → DISPONIBLE ✓ recién acá se vende

Ideas clave para decir

  • Doble control: primero se verifica el contenido del bulto y después el remito (el documento). La mercadería pasa a disponible recién cuando están verificados los dos.
  • Rechazo sin ventana de riesgo: si el precinto llega roto, en el mismo momento de la recepción el bulto queda rechazado. Nunca hay un instante en el que esa mercadería sea vendible.
  • Trazabilidad: cada cambio de estado deja un registro con fecha, estado anterior, estado nuevo y motivo. Ese historial no se edita ni se borra; la base de datos también lo impide.
  • Sin atajos: no se puede pasar de Preparado a Verificado ni reabrir un bulto rechazado.
¿Rechazado es una pérdida o una devolución? Ninguna de las dos: la mercadería queda en custodia del local, bloqueada para la venta. No suma stock vendible ni mueve caja.

4Por qué elegimos cada patrón

Stateciclo de vida del bulto

El problema: lo que se puede hacer con un bulto depende del estado en que está. Sólo se despacha si está precintado y sólo se verifica si fue recibido. El enunciado dice que este ciclo se evalúa críticamente.

Por qué State y no condicionales: con if cada operación preguntaría por todos los estados, y las reglas de un mismo estado quedarían repartidas en cinco métodos. Con State, cada estado es una clase que sabe qué permite y a qué estado pasa. Lo que no permite se rechaza por defecto, así que es imposible saltear la verificación.

Lo que ganamos: las reglas de cada estado quedan juntas, para agregar un estado alcanza con una clase nueva y toda transición pasa por un único punto que deja el registro en el historial. El costo: siete clases chicas.

Strategyagrupación del reporte de ventas

El problema: el reporte de ventas e ingresos tiene que poder verse por día, por local o por medio de pago. El cálculo es el mismo y cambia sólo la forma de agrupar.

Por qué Strategy: cada forma de agrupar es un algoritmo intercambiable y la elige el usuario desde afuera. Ese es exactamente el caso de Strategy. El reporte no tiene un if por agrupación: le pide la clave a la estrategia que recibió.

Lo que ganamos: agregar una agrupación nueva (por ejemplo, por categoría) es agregar una clase. Honestidad: con tres opciones, un if también funcionaría. Elegimos el patrón porque el problema encaja con lo que resuelve Strategy y el enunciado pide dos patrones aplicados a problemas reales.

¿Por qué no Singleton, Factory, Observer o Iterator? No encontramos un problema del dominio que los necesite, y meter un patrón sin un problema real que lo justifique es sobreingeniería. Por ejemplo, con un Singleton los tests no podrían usar cada uno su propia base.

State vs Strategy, en una frase

Strategy responde “¿qué cálculo uso?” y lo elige el usuario desde afuera. State responde “¿qué se puede hacer ahora?” y lo decide el propio objeto según su estado.

6Roles de usuario

Respuesta honestaNo implementamos usuarios, login ni permisos. Fue una decisión del grupo: el enunciado no pide autenticación ni perfiles, así que lo dejamos fuera del alcance para concentrarnos en lo que sí se evalúa (procesos, validaciones, ciclo del bulto, patrones y reportes). Sí identificamos los actores del dominio, es decir quién hace cada cosa en el negocio, y el sistema está organizado según esas responsabilidades.
Si pregunta “¿y cómo lo agregarían?”: se sumarían una entidad Usuario con su rol y su local asignado, un login en el backend Python y un control antes de cada operación. Por ejemplo, el cajero sólo vende en su local y únicamente el receptor verifica bultos. Como la API ya separa cada proceso en su propio endpoint, el control se agrega en esa capa sin tocar las reglas del dominio. Además, cada operación podría guardar quién la hizo, lo que reforzaría la trazabilidad.

Composición vs agregación

Criterio de la cátedra: ¿la parte puede pasar a otro contenedor? y ¿tiene sentido sin contenedor? Si las dos son “no” → composición.

Cómo se ve en el código

◆ Composiciónbackend/dominio/ventas.py · clase Venta

    # Composición: la venta crea sus líneas, cobros y comprobante y valida todo antes de existir.
    detalles = []

        detalles.append(DetalleVenta(self, numero, producto, cantidad, precio, costo))

        registrados.append(Cobro(self, numero, medio, importe))
    self._cobros = tuple(registrados)
    if cobrado != self.total_centavos:

    self._comprobante = Comprobante(self)

Cómo se ve que es composición: la Venta crea sus partes (no las recibe hechas) y les pasa self, así que cada parte pertenece a esa venta y a ninguna otra. Las guarda en tuplas, y no hay métodos agregar_detalle ni quitar_cobro: las partes nacen y viven con la venta.

Cómo se ve que es agregación: la necesidad tiene identidad y ciclo de vida propios. La crea el registro, no la orden, y puede quedar pendiente sin orden. La orden sólo recibe una referencia a una necesidad que ya existía. Ojo: en este mismo código, OrdenReposicion → DetalleReposicion sí es composición, porque la orden crea sus detalles.

Si pregunta “¿y en Python cuál es la diferencia sintáctica?”: ninguna. Las dos se implementan con referencias. La diferencia es de diseño: quién crea la parte (el todo o alguien externo), si se puede transferir o quitar y si existe sin el todo.

Encapsulamiento

  • Estado en atributos con _ y lectura con @property sin setter → bulto.estado = "VERIFICADO" da AttributeError.
  • Los cambios son mensajes con nombre del dominio (precintar, verificar, cambiar_precio, desactivar) que validan antes de modificar.
  • Cada validación vive en el dueño del estado: Producto su precio, Venta que cobros = total, Inventario que ningún saldo quede negativo.
  • Colecciones expuestas como tuplas: nadie recibe la lista interna.

¿Por qué Ubicacion no tiene subclases Local y CD? Tienen los mismos datos y operaciones; sólo cambia qué aceptan (el CD no vende). Se usa un atributo tipo. Herencia sólo porque dos clases se parecen es lo que el material dice evitar.
¿Dónde está el stock? No es un número en Producto: lo lleva Inventario por (ubicación, producto, condición), y cada cambio deja un MovimientoStock.

def ejecutar_transaccion(self, operacion, *argumentos):
    """Confirma todos los cambios o ninguno."""
    conexion = self.conectar()
    try:
        resultado = operacion(conexion, *argumentos)
        conexion.commit()
        return resultado
    except Exception:
        conexion.rollback()
        raise
    finally:
        conexion.close()

  • SQL parametrizado con ?, nunca concatenado (evita inyección SQL). executemany para las líneas.
  • rollback() sólo deshace lo no confirmado. Cerrar la conexión no confirma.
  • Un SELECT no lleva commit() (consultar).

Respuesta cortaEl bulto pasa por Preparado → Precintado → En tránsito → Recibido → Verificado, o termina Rechazado (precinto roto) o Anulado. Cada transición queda registrada en un historial que no se edita ni se borra, y la mercadería sólo queda vendible cuando se verifican el bulto y el remito.

Trazabilidad inmutable — tres capas de protección

Rechazo logístico: en EnTransito.recibir, si el precinto está roto o no coincide, en la misma operación pasa a RECIBIDO y RECHAZADO, el stock va a RECHAZADO y el remito a RECHAZADO. Nunca existe un momento con stock habilitado.
¿Por qué el remito no usa State? Sólo tiene EMITIDO → VERIFICADO o RECHAZADO, una única vez. Un patrón ahí sería sobreingeniería.

6¿Por qué usamos @abstractmethod?

Respuesta cortaEstadoBulto y EstrategiaAgrupacion son contratos: definen qué mensajes debe entender cualquier estado o estrategia, pero no tiene sentido crear “un estado genérico”. Con ABC + @abstractmethod, Python impide instanciar la clase abstracta y obliga a cada subclase a implementar esos métodos; si alguna se olvida, falla al crearla (TypeError), no más tarde.
from abc import ABC, abstractmethod

class EstadoBulto(ABC):                  # logistica.py
    @property
    @abstractmethod
    def nombre(self): ...               # cada estado DEBE decir su nombre

    @property
    @abstractmethod
    def descripcion(self): ...

    def precintar(self, bulto, ...):     # concreto: rechaza por defecto
        self._rechazar(bulto, "precintar")

class EstrategiaAgrupacion(ABC):         # reportes.py
    @property
    @abstractmethod
    def nombre(self): ...

    @abstractmethod
    def clave(self, movimiento): ...    # cada estrategia DEBE saber agrupar
  1. No instanciable: EstadoBulto() da TypeError.
  2. Contrato obligatorio: una subclase que no implemente clave o nombre tampoco se puede instanciar.
  3. Habilita el polimorfismo: Bulto y ReporteVentas envían mensajes al tipo abstracto sin conocer la clase concreta y sin isinstance/if.
  4. Clase abstracta ≠ interfaz pura: EstadoBulto mezcla abstractos (nombre, descripcion) con concretos por defecto (las operaciones rechazan). EstrategiaAgrupacion se parece más a una interfaz: sólo abstractos.
¿Por qué precintar, despachar… NO son abstractas? Si lo fueran, cada uno de los 7 estados tendría que implementar las 5 operaciones, casi todas sólo para rechazar → código repetido. Al dejarlas concretas con rechazo por defecto, cada estado redefine sólo sus transiciones válidas.
¿Se usa super()? En el dominio no hace falta: ninguna derivada redefine __init__. Se usa en ErrorCatalogoAPI(Exception) (api_comun.py): super().__init__(mensaje).
